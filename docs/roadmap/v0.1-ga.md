# Meteorite v0.1 GA Roadmap

Meteorite v0.1 is a service compiler release, not a general-purpose web
framework release. The GA bar is a stable, verifiable path from a Lua-declared
application graph to a deployable Zig service artifact.

## Release Promise

The v0.1 line guarantees these public contracts:

- `meteorite` CLI commands and the Lua route DSL keep their documented v0.1
  behavior unless a release note calls out a compatibility change.
- `meteorite.release({ mode = "static" })` rejects retained Lua runtime nodes
  and produces a self-contained Zig service artifact.
- `meteorite.release({ mode = "hybrid" })` packages only the Lua runtime nodes
  and module trees required by the graph.
- `meteorite-release.json` remains `meteorite.release.v0` for the entire v0.1
  line.
- HTTP TCP, native Unix-socket IPC, and HTTP-over-Unix-socket use the tested
  request, validation, static-asset, and shutdown semantics.

## Supported Matrix

| Release mode | Native host | `x86_64-linux-gnu` | `aarch64-linux-gnu` |
| --- | --- | --- | --- |
| Static | Supported | Supported | Supported |
| Hybrid with PUC Lua 5.4 | Supported | Supported with provenance | Supported with provenance |
| Hybrid Lua C modules | Supported | Supported only after source/rockspec rebuild | Supported only after source/rockspec rebuild |

Cross-target hybrid support requires Moonstone runtime source provenance and,
for every retained C module, source plus rockspec provenance. A release fails
before packaging when those inputs are absent or cannot be rebuilt. PUC Lua 5.4
is the only supported cross-target Lua runtime.

LuaJIT cross-target hybrid, arbitrary Zig target triples, WebSockets, response
streaming, multipart route parsing, trusted-proxy client-IP handling, and
serverless/edge adapters are intentionally unsupported in v0.1. Each must keep
an explicit graph or release-contract diagnostic until a later release defines
its behavior and test matrix.

## Release Checklist

### Contract And Compatibility

- [ ] Review public CLI help, templates, and Lua DSL changes for undocumented
  compatibility breaks.
- [ ] Keep static/hybrid validation diagnostics deterministic and actionable.
- [ ] Verify the release manifest contains no host-only paths or credentials.
- [ ] Record any compatibility exception in the release notes before tagging.

### Test Gate

- [ ] Run `bash tests/repository-hygiene.sh`.
- [ ] Run `bash tests/run-all.sh`.
- [ ] Run `bash fixtures/tests/web-standards.sh`.
- [ ] Run `bash fixtures/tests/ipc-backends.sh`.
- [ ] Run `bash fixtures/tests/basic-service.sh`.
- [ ] Run `bash fixtures/tests/release-smoke.sh`.
- [ ] Run `bash fixtures/tests/ipc-release-smoke.sh`.
- [ ] Run `zig build`.
- [ ] Run `METEORITE_CROSS_TARGET=aarch64-linux-gnu bash fixtures/tests/cross-target.sh`.
- [ ] Run `METEORITE_CROSS_TARGET=x86_64-linux-gnu bash fixtures/tests/cross-target.sh`.
- [ ] Run the aggregate command: `bash tests/release-gate.sh`.

### Release Evidence

- [ ] Create or update the dated release audit in `docs/maintenance/`.
- [ ] Record the commit SHA, Zig version, Lua runtime version, target triples,
  Moonstone provenance result, and every gate result.
- [ ] Build the registry source package and verify generated/build artifacts
  are absent with `bash tests/registry-export.sh`.
- [ ] Publish checksums for distributable release artifacts when artifacts are
  published outside the Moonstone store using `scripts/release-checksums.sh`.

## CI Runner Contract

The release gate needs a runner with Zig 0.16, `moon`, Lua/LuaJIT for host graph
construction, Ballad available as Meteorite's sibling checkout or equivalent
workspace dependency, `file`, `tar`, `lsof`, and a host `luarocks` executable
for Lua C-module rebuild coverage. The runner must execute the matrix from a
clean checkout with a writable Moonstone store and Zig cache.

CI must run the repository-hygiene check on every change. The full release gate
must run for release candidates and tags; it must certify both Linux targets
before v0.1 GA is published.

## Repository Hygiene

- [ ] Keep only benchmark source, manifests, lockfiles, and setup instructions
  under `bench/competitors/`.
- [ ] Never track `node_modules`, Rust `target`, Go build outputs, benchmark
  logs, or generated benchmark results.
- [ ] Never track Ballad/Moonstone/compiler workspaces such as `.ballad/`,
  `.moonstone/`, `.meteorite/`, `.zig-cache/`, `zig-cache/`, `zig-out/`, or
  `dist/`.
- [ ] Use exact package-manager dependency versions and lockfiles where the
  benchmark toolchain produces them for every published comparison.
- [ ] Reject generated benchmark artifacts in the release gate.

## Deferred Work

Feature work that does not close a v0.1 contract, reliability, provenance,
documentation, or release-proof gap belongs after GA. The next roadmap should
choose one focused P1 lane—multipart uploads, response streaming, trusted
proxy policy, or realtime/WebSockets—rather than broaden all web features at
once.
